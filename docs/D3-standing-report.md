## 0. 一句话结论

D3 之前「反关节站不稳」的真凶是**资产里左膝的镜像轴方向写错**（不是限位丢失、也不是 PD 增益抄错）。
修正之后，站立任务在 2048 并行环境下训练，**平均回合长度从 64 步（1.3 s，正好是倒立摆的理论到倒时间）升到 740+ 步（14.8 s）**，
策略确实学会了靠脚踝/髋部策略维持平衡。

## 1. 修掉的那个真凶：左膝镜像轴

### 现象
D2 的限位审计显示 25/25 个关节限位与 URDF 一致，看上去资产没问题。
但运动学测试（`d3_pose_ident.py`）显示：给左右腿下对称的关节角，两只脚的位移**不对称**。

### 定位
逐关节比对左右两侧的 `axis`：

| 关节对 | 右 | 左 | 是否镜像正确 |
|---|---|---|---|
| hip_x | `(1,0,0)` | `(1,0,0)` | ✅（限位区间镜像，轴同向）|
| hip_z | `(0,0,1)` | `(0,0,1)` | ✅ |
| hip_y | `(0,1,0)` | `(0,1,0)` | ✅ |
| **knee_y** | `(0,0,1)` | **`(0,0,-1)`** | ❌ **漏了符号翻转** |
| ankle_y | `(0,1,0)` | `(0,1,0)` | ✅ |

### 为什么这条会直接导致「反关节」
膝盖是**单向限位**（右膝 `[-2.339, +0.061]`，反向余量只有 3.5°）。
镜像约定是「轴线同向 + 角度取反」（`r = -l`）。左膝轴反向之后，它的限位区间也跟着镜像，
于是**物理上允许左膝朝反方向弯**。RL 一定会找到这个解 —— 因为反着弯膝盖在几何上更省力。

### 修法（可复用的做法）
不对某条轴硬编码，而是对每一对镜像关节自动判定：

```
对关节对 (l, r)，设其限位区间分别为 [lo_l,hi_l]、[lo_r,hi_r]
  同号镜像窗口 = 交集宽度，假设 l = +r
  反号镜像窗口 = 交集宽度，假设 l = -r
只有当「同号窗口 < 0.3 rad 且 反号窗口 > 1.0 rad」时才翻转左关节轴
```

这样只翻转真正可疑的 `l_knee_y`，不误伤 `hip_x` / `hip_z`
（它们双向对称，翻转不改变物理，但会破坏 `r = -l` 这个干净约定，
后续所有基于镜像的推理都会变得可疑）。

### 验证
修正后 5 对镜像关节的足端位移完全对称；重建 USD 后限位读数为
`l_knee_y [-0.061,+2.339]` / `r_knee_y [-2.339,+0.061]`，严格镜像。

## 2. 站立姿态与几何（全部实测，不靠推算）

### 2.1 站立高度：0.42125 m

用**迭代收敛法**标定，而不是手算运动学链长：

```
从解析估计值 +30 mm 起步（保证脚一定悬空）
重复：锁住基座 → 量两只脚脚底最低点离世界地面的距离 Δz → 基座下移 Δz
直到 |Δz| < 1e-5
```

为什么从**高处往下逼近**：脚永远悬空，不会穿地，因此整个搜索过程都不受接触力干扰。
实测 3~4 次迭代收敛到 1e-5 m。

| 方法 | 结果 |
|---|---|
| 运动学推算（0.3860 + 0.0350） | 0.42100 m |
| 仿真收敛标定 | 0.42125 m |
| 差 | **0.25 mm** |

两条独立路径吻合到 0.25 mm，这个高度可以直接写进环境配置的 `init_state.pos.z`。

> ⚠️ 踩过的坑：上一版脚本把脚部 STL 的 **z 轴**当成竖直方向，得到脚底偏移 0.0441 m、
> 站立高度 0.430 m。真相是脚点 mesh 的 **y 轴**才是竖直（`sole_y = -0.0350`），
> z 轴是前后方向（脚长 0.115 m，不是 0.045 m）。
> 结果基座被抬高 9 mm、脚其实悬空，所有"有接触"的假设整体失效。
> **教训：STL 没有轴标签，"哪一维竖直"不能靠"哪一维跨度最小"来猜，
> 要用物理量级判断（脚厚只有几厘米，脚长十几厘米）。**

### 2.2 支撑多边形与静态稳定性判据

判据：**质心水平投影是否落在双脚脚底接触点的凸包内**。

为什么不用「放开后能不能自己站住」：直立是**不稳定平衡**（倒立摆时间常数 √(h/g) ≈ 0.22 s），
任何姿态放开都会倒 —— 那正是 RL 要学的东西。所以判断"姿态对不对"必须用静力学判据。

零位姿态的实测结果：

| 量 | 值 |
|---|---|
| 支撑多边形 x 跨度（左右） | 0.1405 m |
| 支撑多边形 y 跨度（前后） | 0.1146 m |
| 质心水平投影 | (0.0000, −0.0079) m |
| **到最近倾覆边的距离** | **+28.7 mm（在支撑内）** |
| 质心高度 h_com | 0.4886 m |
| 倒立摆时间常数 τ | 0.223 s |

支撑多边形顶点（世界系 xy，逆时针）：
```
(-0.0702,-0.0656) → (+0.0639,-0.0939) → (+0.0704,-0.0639) → (+0.0629,+0.0149)
→ (+0.0247,+0.0207) → (-0.0247,+0.0207) → (-0.0633,+0.0140)
```

**关键读法**：质心离脚跟那条倾覆边只有 28.7 mm —— Poppy 的脚只有 4.6 cm 宽、11.5 cm 长，
质心在脚掌中央附近，容错本来就小。这不是 bug，是这个小机器人的固有难点。

### 2.3 动力学对照（只作参考，不作判据）

从标定站立高度 +4 mm 放开，零位姿态：

| 时刻 | 机身倾角 |
|---|---|
| 0.1 s | 0.02° |
| 0.3 s | 0.23° |
| 0.5 s | 0.74° |
| 到倒时间 | **1.35 s** |

0.5 s 内只倾 0.74°，1.35 s 才倒 —— 说明零位姿态的质心几乎正对支撑中心，
平衡很"中性"，符合"这是一个好的 rest pose"的判断。

## 3. 三个致命的方法论坑（本批次最大的收获）

### 3.1 `write_data_to_sim` —— 差点让我去改 PD 参数

写独立探针脚本时，下面这段代码是**错的**：

```python
robot.set_joint_position_target(target)   # 只把目标写进【内部缓冲】
sim.step()                                # ← 目标永远没进 PhysX
```

Isaac Lab 的文档写得很清楚：

> `set_joint_position_target`: "This function **does not apply** the joint targets to the
> simulation. It only fills the buffers with the desired values.
> To apply the joint targets, call the `write_data_to_sim` function."

于是 PhysX 里的驱动目标一直停在 0（初始化时的默认值），关节被"按"在零位。表现是：

| 观测 | 值 |
|---|---|
| 实测"跟踪误差" | **恒等于指令值本身**（指令 0.2 就显示 0.20000）|
| 关节速度 | 恒等于 0.00000 |
| 对 kp 的敏感性 | **完全无**（kp 从 6 到 100，误差几乎不变）|

这三件事放在一起是**物理上不可能**的（如果刚度不够，误差应该 ∝ 1/kp）。
我当时的反应是"改 kp 试试"，这是错的。

**正确反应：当实测结果物理上不可能时，先验证数据通路本身，不要再调参数。**

定位方式是写一个最小化的四段通路自检（`d3_joint_io_check.py`）：

| 段 | 验证什么 | 判读 |
|---|---|---|
| A | 写入一个互不相同的模式，读回来 | 不匹配 → 写/读顺序有问题 |
| B | `robot.data.joint_pos_target` 缓冲 | 目标没进缓冲 → `set_joint_position_target` 写错对象 |
| C | 给远离平衡的目标，看关节是否移动 | 不动 → 驱动器没出力；冲到限位 → 刚度≈0 |
| D | 直接读 USD 里的 `drive:...:stiffness` | 反推 API 的单位 |

为什么平时写训练代码从不踩这个坑：`ManagerBasedRLEnv.step()` 内部会调
`scene.write_data_to_sim()`，这一步由框架代劳。只有写独立探针脚本时才需要自己补。

### 3.2 三层单位约定（再确认一次）

| 层 | 单位 | 证据 |
|---|---|---|
| URDF `<limit effort>` | N·m | MX-28 写 3.1 |
| `ImplicitActuatorCfg.stiffness` | **N·m/rad** | 与直觉一致，可直接物理填 |
| USD `drive:angular:physics:stiffness` | **N·m/deg** | 配置写 8.0 N·m/rad，USD 读到 **0.1396 = 8/57.296** |

**把 USD 里的数抄进配置会软 57.296 倍。**

### 3.3 `applied_torque` 对 implicit 执行器恒为 0

PhysX 不暴露隐式驱动的力矩，所以 `robot.data.applied_torque` 永远是 0。
要拿计算力矩得用 `robot.data.computed_torque`（Isaac Lab 自己按 PD 公式算的近似值）。
另外，稳态的时候有更干净的算法：**速度≈0 时 `τ = kp × 稳态误差`**，
直接从可测量反推该关节实际承担的重力矩，不需要去挖 PhysX 内部量。

## 4. PD 增益：从"猜"改成"设计"

### 4.1 设计公式

```
kp = 力矩上限 / 设计偏角
kd = 2·ζ·sqrt(kp·J_eff)      （临界阻尼关系）
```

- **为什么要除以"设计偏角"**：kp 的物理含义是"每 1 rad 偏差产生多少力矩"。
  取设计偏角 0.2 rad（11.5°）的意思是"关节承受满力矩时允许偏 11.5°"，
  这个尺度既有物理含义，也和舵机的实际柔顺性相符。
- **为什么 kd 是 sqrt(kp) 而不是 kp 的线性函数**：
  单关节 PD 闭环固有频率 ω = √(kp/J)，临界阻尼要求 kd = 2Jω = 2√(kp·J)。
  按线性给，kp 变大时会过阻尼（响应迟钝）；给固定值则欠阻尼（高频抖动，
  在 PhysX 里表现为关节嗡嗡响、训练时动作高频振荡）。

### 4.2 取值

| 关节组 | 力矩上限 | kp | kd |
|---|---|---|---|
| hip_x / hip_z / knee_y / ankle_y（MX-28） | 2.5 N·m | **12.5** | 1.00 |
| hip_y（MX-64） | 6.0 N·m | **30.0** | 1.55 |

两组 kp 的比值 2.4 **正好等于力矩比 6.0/2.5** —— 这比"审计报告说 hip 是 2.5 倍"更有依据。

### 4.3 一个反直觉但重要的实测结论

悬空法实测（基座抬高 3 cm，脚完全离地，只受重力）：
**站位/屈膝姿态下各关节承担的重力矩几乎为 0（< 5e-5 N·m）。**

也就是说 —— **"Poppy 站不住"的主因不是"关节刚度不够"，而是平衡本身是倒立摆问题。**
PD 稳态误差在零位姿态下只有 0.0003 rad 量级。
这个结论直接决定了 D3 的定位：**它主要是一个 RL 平衡任务，不是参数标定任务。**

### 4.4 已知未定项（诚实记录）

#### ~~屈膝姿态的踝补偿解不出来~~ → **D4 已推翻：这是本报告的一个错误结论**

本报告初版写的是：

> `髋 = +k/2, 膝 = −k, 踝 = +k/2` 并**不能让脚掌水平** —— 脚掌倾角恰好等于 `k`。
> 说明三根俯仰轴的方向并不像我假设的那样简单相加。

**这个结论是错的，而且错在测量工具本身。** D4 用实测雅可比 + 回代验证推翻了它：

1. **实测雅可比**（`scripts/d4_foot_frame_solve.py` Part 2，中心差分 δ=0.05，
   在零位和 k=0.20 两个工作点各测一遍）：
   ```
   右腿  ∂θ/∂hip_y = -1.0000   ∂θ/∂knee_y = -1.0000   ∂θ/∂ankle_y = -1.0000
   左腿  ∂θ/∂hip_y = +1.0000   ∂θ/∂knee_y = +1.0000   ∂θ/∂ankle_y = +1.0000
   ```
   即 **θ = ∓(hip_y + knee_y + ankle_y)**，三根俯仰轴**同号**相加 ——
   和本报告原本的假设完全一致。

2. **那"倾角恰好等于 k"是怎么来的？** 是 `d3_pd_calib.py` 的 `build_pose()`
   把镜像符号 `s` 也乘到了踝关节上：

   ```python
   for side, s in (("r", -1.0), ("l", +1.0)):
       pose[f"{side}_knee_y"]  = s * k
       pose[f"{side}_hip_y"]   = -s * (k / 2.0)
       pose[f"{side}_ankle_y"] = s * (k / 2.0)     # ← 用了 s（和 knee 同号）
   ```

   于是右腿实际被摆成的是 `(hip, knee, ankle) = (+k/2, −k, **−k/2**)`，
   **角度和 = −k**，而报告里写的是 `(+k/2, −k, +k/2)`（角度和 = 0）。
   按 `θ = −Σ` 算，倾角当然恰好等于 k。D4 同时测了这两种摆法：

   | k | 实际摆法 (hip, knee, ankle) | Σ | 倾角 |
   |---|---|---|---|
   | 0.20 | (+0.10, −0.20, **−0.10**) ← D3 脚本实际摆的 | −0.20 | **11.4592°** |
   | 0.20 | (+0.10, −0.20, **+0.10**) ← 报告里写的 | 0.00 | **0.0000°** ✔ |

3. **正确解**：`hip_y = +k/2`（位置）、`ankle_y = +k/2`（姿态）——
   即 **踝与髋同号、与膝反号**。k=0.05~0.30 全程实测脚掌倾角 0.0000°（双脚）。

**教训（比结论本身更值钱）**：
> 当"实测"和"解析"矛盾时，不要默认实测是对的。
> 实测也只是另一个程序，程序一样会写错符号。
> 正确动作是**回头分别验证双方各自的前提**：
> 这次是先测出雅可比（把"方向"这个前提单独量出来），
> 矛盾就自动指向了"姿态构造函数"而不是"物理"。
> —— 顺手复现了 3.1 的同一类坑：**上次是漏调 API，这次是乘错符号，
> 都是"用错误的工具得到了看似明确的数字"。**

**对 D3 自身结论的影响：无。** D3 用的是零位姿态（各关节 0，任何符号约定下
角度和都是 0，脚掌本来就水平），所以里程碑 1 的结论与训练结果全部有效。

D4 的默认姿态已按上面的解写成 `assets/poppy.py` 的 `walk_default_joint_pos()`：
`r = (+0.100, −0.200, +0.100)`、`l` 取镜像，站立骨盆高 0.41919 m。

## 5. 环境设计（`source/poppy_walk`）

### 5.1 为什么做独立扩展包

保持 Isaac Lab 上游原样。改上游会把代码和它的安装路径绑死，
换机器/升级都要再打补丁；而且面试时说不清"哪部分是自己写的"。

训练入口是薄壳 `scripts/train_poppy.py`：
先 `import poppy_walk`（触发 `gym.register`，且是**轻量**导入 ——
env_cfg/agent_cfg 写成字符串延迟导入，不会在 SimulationApp 启动前拉起 torch/omni），
再 `runpy` 执行官方 `train.py`。

### 5.2 关键配置与它们各自防的失败模式

| 配置 | 防的失败模式 |
|---|---|
| 速度指令范围全设为 0 | 同一套环境从"速度跟踪"退化成"保持静止"，D4 只需打开 ranges |
| `base_height_l2` 目标 0.421 m | **防"蹲着不动"作弊解**：蹲姿质心更低更好平衡，不给高度奖励策略必然发现它 |
| 观测拆 policy / critic 两组 | 非对称 Actor-Critic：`base_lin_vel`/`base_pos_z` 真机需状态估计，只喂价值网络降 advantage 方差 |
| `init_state.pos.z = 0.42125` | reset 不发生下落冲击（否则落地冲击被策略当成噪声）|
| `init_state.rot` 绕 Z +90° | 把 Poppy 的"前方 = −Y"对齐到 Isaac Lab 的 +X，否则 `lin_vel_x` 语义错位且从曲线上看不出来 |
| 不加 `joint_pos_out_of_limit` | PhysX 关节限位本就是硬约束；且 Isaac Lab v2.1.0 这个函数有索引 bug |
| `bad_orientation` 取 50° | 60° 时永不触发（高度判据先到，对应 53.5°），30° 会打断横向欠驱动的正常恢复摆动 |

### 5.3 观测空间（实际打印核对）

```
Actor MLP:  Linear(39 → 128) → 128 → 128 → Linear(128 → 10)
Critic MLP: Linear(43 → 128) → 128 → 128 → Linear(128 → 1)
```

- Actor 39 维 = 角速度 3 + 投影重力 3 + 速度指令 3 + 关节角 10 + 关节速度 10 + 上一步动作 10
- Critic 43 维 = Actor 39 + 基座线速度 3 + 基座高度 1 ← **特权观测通路确认生效**

### 5.4 已知建模差异（不掩盖）

URDF 总质量 **2.607 kg**，真机标称 **3.5 kg**（差电池 / 树莓派 / 结构件）。
不做手工补偿 —— 手工补质量会改变质心高度和惯量分布，那是个更大的假设。
改为在 D6 用域随机化覆盖，并在这里记为已知 gap。
**影响**：仿真里力矩需求偏低，站立会比真机更容易。面试被问到时如实说明。

## 6. 训练结果

配置：2048 并行环境，PPO，`num_steps_per_env=24`，`max_iterations=1200`，seed 42，headless。

| 迭代 | 平均回合长度 | 平均回报 | 动作噪声标准差 |
|---|---|---|---|
| 9（随机策略） | 64 步（1.28 s） | −4.71 | 0.99 |
| 140 | 740 步（14.8 s） | +19.9 | — |
| 181 | 729 步 | +20.8 | 0.30 |
| （待补） | | | |

**读法**：
- 第 9 轮 64 步 = 1.28 s，正好等于 §2.3 实测的倒立摆到倒时间 1.35 s ——
  说明初始阶段机器人确实是"一放开就倒"，不是别的问题。
- 第 181 轮回合长度 729 步且 `Episode_Termination/time_out` 开始出现（1.25），
  说明有相当一部分回合**活满了 20 s 上限**。
- 动作噪声标准差从 0.99 降到 0.30 → 策略在收敛，探索在收敛，没有发散。

吞吐：**约 41000 环境步/秒**（D1 官方 Cassie 基线约 1650 步/秒的 25 倍 ——
Poppy 刚体少、接触对少、且去掉了地形 ray caster）。

## 8. 面试必问（D3 部分提前写答案）

**Q：你怎么确定是资产的问题，而不是算法的问题？**
A：先做静力学判据。直立是不稳定平衡，所以"放开能不能站住"不能作为判据
（任何姿态都会倒）。我用"质心水平投影是否落在支撑多边形内"这个可测量的几何判据，
把"姿态对不对"和"控制行不行"彻底分开。确认姿态在支撑内（余量 28.7 mm）之后，
才敢说问题在控制侧。然后逐关节比对左右镜像轴，发现左膝轴漏了符号翻转。

**Q：训练不收敛时你的排查顺序是什么？**
A：先验证数据通路，再看物理，最后才调参数。
这一版就踩过：实测误差恒等于指令值、且对 kp 完全不敏感 —— 这个组合物理上不可能。
我当时写了个四段通路自检（写/读/驱动/USD），5 分钟定位到缺了一行
`robot.write_data_to_sim()`。如果当时去调 PD 参数，可以浪费一整天。

**Q：为什么观测里要拆 policy / critic 两组？**
A：`base_lin_vel` 和 `base_pos_z` 在真机上要靠状态估计才能拿到，且噪声大，
所以策略不该依赖它们。但价值网络只是在训练时估回报，给它更准的状态能降低
advantage 的方差、加速收敛。这就是非对称 Actor-Critic 的动机：
**"训练时能用、部署时不能用"的信息，正好放进 critic。**
